# Events

An Event is a one-off tournament, distinct from a recurring League — has its own staff, registration/waitlist, optional decklist submission, and archetype tracking. It pairs nothing itself: rounds and matchups arrive by importing the `.tdf` file the official TOM software writes (see [TOM import](#tom-tdf-import-0041) below), unlike league sessions which run their own Swiss.

## Routes

- `app/events/[slug]/page.tsx` — main event detail page, organised like the session page: pinned above the fold are the header (name, game/category badges, subtitle, status, meta line, archetypes/display links), the viewer's own pairing (`EventMyMatch`), prizes, the registration/list form (`EventRegister`) and the self-service archetype picker (locked once event is `complete`) — registration and archetypes stay out of the tabs on purpose, they're the two things a player comes here to do. The registration card disappears once entry is closed (PL-28, see the cutoff section below): past the cutoff or on a closed/complete event only a viewer who is registered still gets it, read-only. Everything else sits in the `PageTabs` strip: **Emparejamientos** (`EventPairings`, only once a `.tdf` has been imported), **Clasificación** (TOM's final placings if the tournament is closed, otherwise the provisional table), **Inscritos (n)** (admins and event staff — check-in tally, roster with `ParticipantsList`, waitlist, Pokémon-ID copy tool; staff get it read-only, see [Staff access](#staff-access-to-the-roster-and-lists-0049-pl-22)), **Importar TOM** (admin only, PL-26 — the one-step `TdfImport` file drop, the "última importación" line and the "borrar lo importado" undo; always the second tab for whoever can see it, so it sits right after Emparejamientos once there are rounds and right after Inscritos before that), **Gestión** (admin only — staff roster + add-staff/create-staff-player forms, edit form `EditEventForm`, status toggle open/closed/complete, and the site-admin-only hard delete). Admins and staff land on Inscritos while nothing has been imported yet (check-in, collecting IDs and deck checks are the job at that point), everyone else on Emparejamientos, falling back to the first tab that exists. `?tab=<value>` overrides that landing when it names a tab that exists: the tab strip (`PageTabs`) keeps the active tab in the URL, which is how the import action lands the TO on Emparejamientos and how a tab can be linked. The staff panel is the one thing that moves: admins get it inside Gestión with its forms, non-admins get the read-only list pinned above the tabs, since who's judging is public but the forms aren't. Nobody else sees the roster: it carries player IDs and every submitted list, so it's admin/staff-only in the UI (note the underlying `event_registrations` rows are still world-readable by RLS — only `event_lists` is actually restricted). `EventRealtimeRefresher` mounts while the event has imported rounds and isn't `complete`.
- `app/events/[slug]/arquetipos/page.tsx` — public archetype-stats sub-page; renders `computeEventArchetypeStats(event.id)` in an `ArchetypeStatsTable`. Usage (players, % of field) always shows; the win/loss/win-rate columns appear only for events whose results were imported from TOM, since an event with no import has nothing to put in them.
- `app/events/[slug]/display/page.tsx` — venue projector view, the event twin of the session display: the current round of every age division at across-the-hall size, standings beside it, realtime-refreshed, nothing to click. No round clock — TOM runs its own. A table that has reported but isn't in TOM yet shows its winner like any other, tagged "Sin confirmar" instead of "Pendiente", so the room can see which tables are still waiting on the judge. Shows TOM's official placings once the event is closed, the provisional table before that. Linked from the event header whenever imported rounds exist.
- `app/events/page.tsx` — public index of every standalone event (PL-30), the history the landing page cannot give: `listEvents()` split by `splitEventHistory` (`lib/event-history.ts`) into **Próximos** (soonest first) and **Anteriores** (newest first, each row with its status badge so an old cup left in Cerrado is visible as such). An event is past once its status is `complete` or it started before the start of today (app timezone, `startOfTodayIso`), the same cutoff the landing feed uses, so a cup sits under Próximos the whole day it runs. Filters `?game=tcg|vgc` and `?category=<cup|challenge|demo|prerelease|others>` (`buildFilterHref`) apply to both sections; the chips only render when there is at least one event. Rows are `UpcomingRow` (`variant="list"`, `trailing` slot for the badge) fed by `eventToUpcomingItem` from `lib/agenda.ts`, so it looks like the landing's Próximos list. Linked from the site header ("Eventos", between Ligas and Arquetipos). The original `/events` index was dropped in July as redundant with the landing page; this one exists precisely because the landing page hides anything that already happened.
- `app/admin/events/page.tsx` — admin-only (`requireAdmin`) page hosting `CreateEventForm` to create a new standalone event. Loads every league (id, name, `play_league_id`, archived) for the form's league picker and the Play! Pokémon paste (see below).
- `app/admin/events/import/page.tsx` — admin-only (`requireAdmin`) import page (PL-21): queries pokedata.ovh for the League Cups / Challenges announced around Granada, resolves each against our stores and season leagues and creates the ticked ones through `create_event`. Linked from `/admin/events`. See [Import from the locator](#import-from-the-locator-pokedataovh-pl-21).

## Server actions (`app/actions/events.ts`)

All are `"use server"`, validate/cap input then call Supabase RPCs; most `revalidatePath`.

- `createEventAction` — validates + calls `create_event` RPC, redirects to the new event. Since 0044/0045 it also passes `p_store_id`, `p_league_id`, `p_tournament_id` (≤40 chars, `[\w.-]`) and `p_status` (open/closed/complete, the initial status — a pasted page whose Status is already Complete is created straight into `complete`). A duplicate tournament id (RPC raise or the partial unique index) is translated into "Ya existe un evento con el Tournament ID …".
- `updateEventAction` — direct `.update()` on the `events` table (not an RPC); also writes `store_id`, `league_id` and `tournament_id` with the same duplicate translation.
- `importPokedataEventsAction` (`app/actions/pokedata.ts`) — site admin only; takes the ticked tournament ids, re-queries pokedata.ovh server-side, resolves store (Play! League ID → `stores.play_league_id`) and season (`matchSeasonLeague`) again and calls `create_event` once per event (status `open`, cost/location/URL from the API, no capacity; `p_list_required` and `p_allow_guest_lists` both on for cups and challenges via `requiresListByDefault`, off otherwise — PL-24). Returns one result per event (slug or readable error); a duplicate tournament id reads as "Ya existe un evento con el Tournament ID …".
- `registerEventAction` / `submitListAction` — register (with optional list) / update submitted list via `register_event` / `submit_event_list` RPCs. Both refuse once the entry deadline has passed (`entryDeadlineError` helper, skipped for event admins) before even calling the RPC, so the user gets a Spanish message instead of the raw SQL error.
- `adminSubmitListAction` — admin bypass: writes any registrant's list via `admin_submit_event_list`, deadline or not.
- `guestSubmitListAction` / `guestUpdateListAction` — logged-out registration + list for events with `allow_guest_lists` (see [Guest lists](#guest-lists-0048-pl-19)). Validate name, Pokémon ID (1–10 digits, whitespace dropped) and that a list or URL is present, call `guest_submit_event_list` / `guest_update_event_list`, translate the RPC's English errors (`friendlyGuestError`) and, on submit, set the `event_guest_<eventId>` httpOnly cookie with the token the RPC returns. Their state type is `GuestActionState` (`ActionState` + `token`).
- `setMyEventArchetypesAction` / `adminSetEventParticipantArchetypesAction` / `setEventArchetypeVisibilityAction` — self vs admin archetype-pick RPC wrappers.
- `unregisterEventAction` / `adminRemoveRegistrationAction` — leave / admin-kick a registrant.
- `adminSetEventCheckedInAction(slug, eventId, playerId, checkedIn)` — on-site check-in toggle via `admin_set_event_checked_in`. The page binds `slug` so the shared roster can call it with the session-style `(contextId, playerId, checkedIn)` signature.
- `setEventStatusAction` — open/closed/complete toggle.
- `addEventStaffAction` / `createEventStaffPlayerAction` / `removeEventStaffAction` — staff management, including creating a "managed" player record for staff not already in the system.
- `deleteEventAction` — hard delete via `delete_event` RPC, redirects home.

## Server actions (`app/actions/event-tdf.ts`)

- `importTdfAction` — the whole import in one step (PL-26; until then it was a read → review → confirm pair, with `previewTdfAction` showing the suggested player matches for the TO to override): reads the uploaded file (2 MB cap), parses it, resolves every TDF player with `matchTdfPlayers` (existing mapping → `pokemon_id` → unambiguous name → `null`, which `import_event_tdf` turns into a new managed player), calls the RPC, revalidates and `redirect`s to `/events/<slug>?tab=pairings`. Nothing from the browser is trusted beyond the file. Only errors (unreadable file, RPC failure) come back as state; admin-gated in the action itself, not just the UI. A wrong name match is fixed by "borrar lo importado" and re-importing once the player carries the right Pokémon ID — there is no per-player override any more.
- `reportEventMatchAction` — a player's own call on their match, via `report_event_match`.
- `clearEventTdfAction` — admin undo, via `clear_event_tdf`.

## Lib logic

- `lib/event-history.ts` (pure, unit-tested in `event-history.test.ts`) — `splitEventHistory(events, cutoffIso)` → `{ upcoming, past }` for `/events` (PL-30): past = `status === "complete"` or `starts_at < cutoff`; upcoming sorted soonest first, past newest first, undated events last in both (creation order).
- `lib/tdf.ts` (pure, unit-tested in `tdf.test.ts`) — the `.tdf` parser. Carries a minimal XML reader rather than a dependency (`parseXml`; tolerant, but a literal `>` inside an attribute value would confuse it — TOM escapes those). `parseTdf` returns tournament meta, players (`userid` = Pokémon ID, names, birthdate), a flat round list keyed by pod `category` (age division) + round number, and the final placings from the `<standings>` block once the tournament is closed. `TDF_OUTCOMES` maps TOM's numeric `outcome` (0 pending, 1/2 win, 3 draw, 4 double loss, 5 bye) — an unknown code falls back to pending and the raw code is kept. `pairKeyOf` builds the sorted-userid natural key that makes re-imports idempotent. `matchTdfPlayers` resolves TDF players against the player table in order: existing mapping → `pokemon_id` → unambiguous accent-insensitive full name → nothing (a name matching two players deliberately resolves to nothing).
- `lib/event-rounds.ts` — read side of the import: `getEventRounds`, `getEventMatches` (stable order: table, byes last, then created_at), `getEventStandings` (official placings), `getEventTdfMapping` (userid → player id, admin-only by RLS), `getLastTdfImport`.

### What the file format actually does (learned from a full real tournament)

Three things in the format are traps, all of them verified against every export of one real event (`lib/tdf-sequence.test.ts` replays all 13 files and asserts the end state; it skips itself when the fixtures aren't present, since they carry real names and birthdates and live outside the repo):

- **The pod's `stage` is progress, not identity.** It reads 0 while the swiss runs and flips to 1 the moment the cut is paired — under the same rounds. Keying rounds on it duplicates the entire swiss at top-8 time. Rounds are keyed on `(event, division, number)` only, and the parser pointedly does not read pod `stage`.
- **Top-cut rounds continue the swiss numbering.** A 4-round swiss plus a top 4 runs 1..6 in one pod; what marks the cut is the round's own `type` (3 = swiss, 1 = single elimination), which is what `isFinals` comes from. The UI names those rounds by how many tables are left ("Semifinales", "Final") because "Ronda 5" tells a player nothing.
- **A player's `userid` can change mid-tournament, and TOM rewrites history.** In the real data a placeholder ID (`1999999`) was corrected to the entrant's real one (`6054871`) after round 2, and every earlier round in later exports came back re-written to the new ID. This self-heals: the name match in `matchTdfPlayers` lands the new userid on the existing player, and because pairings are keyed by `pair_key`, the re-written round-1 pairing inserts under the new key and the stale one is swept by the same delete that handles a re-pair. Both userids end up mapped to one player.

Two smaller confirmed details: `<standings>` is a sibling of `<pods>`, and its per-division `<pod type="finished">` entries are placings, not rounds — the parser only walks `tournament > pods > pod`, so they can't be confused. And a **bye** is written as `outcome="5"` on a match holding a single `<player>` element (not `<player1>`) with `<tablenumber>0</tablenumber>`; the parser reads the lone element as player 1 with no opponent and discards table 0, since a bye is played at no table. Verified against a real 15-player export. Outcome code 4 (double loss) is the only mapping still unconfirmed — it has never appeared in real data.
- `lib/play-event-paste.ts` (pure, unit-tested in `play-event-paste.test.ts` against a verbatim real page) — parser for the text of a tournament page on the Play! Pokémon organiser site. See [Play! Pokémon paste](#play-pokémon-paste-0044) below.
- `lib/season-match.ts` (pure, unit-tested in `season-match.test.ts`) — `formatFromPlay` and `matchSeasonLeague`, the store → season resolution described in the paste section.
- `lib/pokedata.ts` (pure part unit-tested in `pokedata.test.ts` against a verbatim API record) — pokedata.ovh client and mapping: `pokedataUrl`, `pokedataWindow`, `tournamentIdFromUrl`, `gameFromPokedataProduct`, `playSeasonQuarter`, `localToIso` (Europe/Madrid wall-clock → instant), `mapPokedataEvent`, `proposedEventName`, `seasonFormatFor`, and the server-only `fetchPokedataEvents`.
- `lib/events.ts` — data-access layer: `EventRow`/`EventStatus` types (with `league_id` / `tournament_id` since 0044, `store_id` since 0045), `listEvents`, `listLeagueEvents(leagueId)` (the league page's "Eventos de la liga" card), cached `getEventBySlug`, `isEventAdmin` (site admin, row in `event_admins`, or admin of the event's store), `isEventStaff` (0049: `event_staff` row whose player is linked to the logged-in user), `listRegistrations`, `getMyRegistration` (joins `event_registrations` + `event_lists`), `listEventStaff`, `getEventLists` (admin/staff-only by RLS, all submitted lists keyed by player). Also `eventEntryDeadline` / `isEventEntryLocked` (+ `DEFAULT_LIST_LOCK_MINUTES` = 60, `MAX_LIST_LOCK_MINUTES` = 10080), the TS mirror of the `event_entry_locked` SQL function used to gate the UI.

## TOM (.tdf) import (0041)

The TO drops the file TOM exports and the site shows the pairings back to the players. **TOM stays the source of truth**: `event_matches.official_result` only ever changes on import, and what a player taps on their phone lands in `reported_result` as a signal for the judge to key into TOM. The two never fight, and the next import doesn't touch what was reported.

The reporting loop is the point: players (or the judge, on any table) tap the result from their seat, the TO reads the round tab — reported tables render as decided with a "Sin confirmar" badge, unreported ones sit blank — types them into TOM, and re-drops the .tdf. The import lands `official_result`, the badge goes away, and the row now says what TOM says. Nothing marks a report as "already entered" beyond that: the import is what clears it, deliberately, so there is no second piece of state to keep honest.

The intended loop is re-dropping the same file after pairing each round — the import is idempotent. Rounds are keyed by `(event_id, division, number)` and pairings by `(round_id, pair_key)`, where `pair_key` is the sorted pair of TDF userids (or `<userid>~bye`), so it survives TOM swapping player 1 and player 2 between exports. Pairings a round no longer lists are deleted, so a re-pair in TOM propagates instead of leaving ghosts. See the format notes above for why the round key is what it is.

`import_event_tdf(p_event, p_tdf_id, p_file_name, p_players, p_rounds, p_standings)` does the whole commit in one transaction: resolves or creates each player (a created one gets `pokemon_id` = the TDF userid), upserts `event_tdf_players`, adds everyone to `event_registrations` **ignoring capacity** (whoever TOM says is playing is playing), upserts rounds and pairings, replaces the final placings wholesale if the file carries any, and records the audit row. `report_event_match(p_match, p_result)` is open to the two players or an event admin. `clear_event_tdf(p_event)` undoes an import but deliberately keeps the players it created and their registrations — by then they may carry archetypes or lists.

Tables: `event_rounds`, `event_matches`, `event_standings` (official placings), `event_tdf_players` (the userid ↔ player mapping) and `event_tdf_imports` (audit). Rounds, matches and placings are world-readable like session pairings; the mapping and the audit rows are admin-only. `event_matches`/`event_rounds` are in the realtime publication. `merge_players` was extended again (on top of 0029) to carry `event_matches` and `event_tdf_players` across a merge — both FKs cascade, so without it a merge would silently delete the source's imported history.

Standings on the page come in two flavours. While the tournament runs there is a **provisional** table computed with `lib/scoring` (the league scorer) off the official results, labelled as such: TOM's full tiebreaker chain is not reproduced, and a TOM double loss is booked as two solo losses, which drops that pair from each other's OWP. Once the TO exports a closed tournament the file carries TOM's own placings, and those replace the computed table entirely.

Known limits, all deliberate:

- **No bracket rendering.** Top-cut rounds show as extra round tabs named by size ("Semifinales", "Final"), not as a bracket.
- **Outcome codes** outside 0–5 fall back to pending; the raw code is kept in `event_matches.official_code` so an unmapped one is inspectable rather than silently scored. Codes 0–3 and 5 are confirmed against real exports; 4 (double loss) is the last unverified one.
- The import does not create the event — it attaches to an event that already exists.

## Entry deadline (0039)

`events.list_lock_minutes` (int, default 60, 0–10080) closes registration *and* list submission that many minutes before `starts_at`. `event_entry_locked(p_event)` is the SQL source of truth — `starts_at is null` or `list_lock_minutes = 0` never locks — and both `register_event` and `submit_event_list` raise once it returns true, unless `is_event_admin(p_event)`. Admins bypass the cutoff entirely and get `admin_submit_event_list(p_event, p_player, p_content, p_url)` to write someone else's list. `create_event` was dropped/recreated with a 13th arg `p_list_lock_minutes`; the value is editable in both the create and edit event forms (minutes before start, 0 = no cutoff). Unregistering is deliberately *not* blocked by the deadline.

In the UI (PL-28) the registration card is gone once entry is closed — cutoff passed, or status not `open` — for everyone, admins included: only a viewer who is registered keeps it, read-only, showing the badge and what they sent ("La inscripción está cerrada." when it's the status that closed it, the cutoff time otherwise). There is no admin bypass on the card any more: admins add players and write lists from the roster tools in Inscritos, which is what the `is_event_admin` bypass in the RPCs is for, and on the day the card at the top only got in the way of the tabs.

## Guest lists (0048, PL-19)

A standalone event can accept lists from people without an account: `events.allow_guest_lists` (bool, default false, a switch in both event forms; `create_event` gained an 18th arg `p_allow_guest_lists`). Since PL-24 the create form turns it — and "Lista obligatoria" — on whenever the category becomes cup or challenge (`requiresListByDefault` in `lib/event-category.ts`, unit-tested), whether picked by hand or filled by the Play! paste, until the TO touches either switch; the pokedata importer applies the same rule, and 0050 flipped the cups and challenges that already existed. When it is on and the viewer is logged out, the registration card on `/events/[slug]` renders `EventGuestRegister` instead of "Entra para inscribirte"; logged-in users never see it. Same closing rule as the account card (PL-28): once entry is closed only a guest arriving through their private link still sees their entry, read-only — no card and no sign-in line otherwise.

Nothing new is invented for the roster. `guest_submit_event_list(p_event, p_name, p_pokemon_id, p_content, p_url)` turns the guest into an unclaimed managed player (`players` row with `display_name` = the name, `pokemon_id`, `user_id`/`created_by` null — or the existing unclaimed player carrying that ID) and then writes a normal `event_registrations` row (same capacity/waitlist rule as `register_event`, `has_list = true`) and a normal `event_lists` row. So the guest shows in the admin roster with a "Sin cuenta" badge (`EventParticipant.has_account`, false for any managed player), counts toward capacity, feeds the Pokémon-ID copy tool, matches on `.tdf` import by ID or name, and can claim the player later from `/me`. A list or URL is mandatory for guests regardless of `list_required`: the whole point of the flow is handing a list in.

The Pokémon ID is the dedupe key and both name and ID are required. The RPC refuses when the flag is off, the event is not `open`, `event_entry_locked` is true (no admin bypass — a logged-in admin is not a guest), the ID is not 1–10 digits, the ID belongs to a player **with** an account ("belongs to a registered user": they must log in), or that player is already registered for the event ("already registered": nobody overwrites a list by typing someone's ID).

Edits work through a token, since a guest has no `auth.uid()`. The submit RPC returns 64 hex chars (two v4 UUIDs, core Postgres only) and stores only their sha256 in `event_guest_entries (event_id, player_id, token_hash unique, created_at)` — RLS on, **no policies and no grants**, so the table is reachable only through the security-definer RPCs. The server action puts the token in an httpOnly cookie `event_guest_<eventId>` (sameSite lax, secure in prod, 60 days, path `/events/<slug>`) and the component also prints it as a private link `/events/<slug>?guest=<token>`. The page resolves the token from `?guest=` first, then the cookie (`lib/event-guest.ts`: `isGuestToken`, `guestCookieName`, `guestEntryPath`…, unit-tested in `event-guest.test.ts`), and calls `guest_get_event_entry(p_event, p_token)` (`lib/events.ts` → `getGuestEntry`), which joins `event_registrations` so a registration the TO removed reads as "no entry" and the blank form comes back. `guest_update_event_list(p_event, p_token, p_content, p_url)` rewrites the list until the deadline. All three RPCs are granted to `anon` and `authenticated`. The private-link origin comes from the request headers (`x-forwarded-host` / `host` + `x-forwarded-proto`), because the component renders on the server too.

Known gaps: no rate limiting on the anonymous RPC beyond the one-registration-per-ID rule and the input caps; a guest cannot unregister themselves (the TO removes them from the roster); merging players (`merge_players`) does not carry `event_guest_entries` across, so a merged guest loses their edit link (the list itself survives with the registration).

Key RPCs: `create_event`, `register_event` (handles waitlist via capacity), `submit_event_list`, `unregister_event`/`admin_remove_registration` (promotes from waitlist), `set_event_status`, `set_event_archetypes` (self-service, locked post-complete unless never set), `admin_set_event_archetypes` (unrestricted), `set_event_archetype_visibility`.

## Staff access to the roster and lists (0049, PL-22)

Judges need the submitted lists to deck-check, but `event_lists` was readable only by the submitter and event admins, and the Inscritos tab was admin-only. Staff are `players` rows (0024), some of them managed players with no login, so the rule is: a staff row whose player is linked to the logged-in user (`players.user_id = auth.uid()`) counts, whatever the free-text role says. Managed staff never log in and never reach the policy.

`is_event_staff(p_event)` (SQL, `security definer`, granted to anon/authenticated) is the check; the `event_lists` select policy is recreated as `event_lists_select_own_admin_or_staff` with it as a third branch. Nothing else in the DB changes: staff cannot write lists (`admin_submit_event_list` still requires `is_event_admin`), check people in, remove registrants or edit archetypes.

The page mirrors that with `isEventStaff` in `lib/events.ts`: `canViewRoster = admin || staffViewer` gates the Inscritos tab, the lists query and the initial-tab choice. For a staff viewer the roster renders read-only — `ParticipantsList readOnly` (static check-in icon, no archetype button), no remove form, `ParticipantListEditor readOnly` (view only), plain names instead of `/admin/players` links under the Pokémon-ID copy tool, and a "Vista de staff" hint at the top of the card. Gestión stays admin-only, and the public staff panel above the tabs is unchanged. An admin who is also on the staff list is simply an admin.

## Play! Pokémon paste (0044)

The organiser site has no API, so a standalone event is created from the page text itself: select-all → copy on the tournament's page, paste into the "Pegar desde Play! Pokémon" box at the top of `/admin/events`, press "Rellenar formulario". The parser runs in the browser (`parsePlayEventPaste`, pure), fills the create form and writes nothing — the TO reviews and submits as usual. The page is a flat list of label / value lines, so the parser walks trimmed non-empty lines and reads the line after a known label:

- title = first line, unless it is a label or parses as a date (League Cups and Challenges have no title on the Play! site — the header repeats the start date — so `name` comes back null for them); `Tournament ID:` / `League ID:` by regex over the whole text (both appear inline in the header and as label+value further down); the start date is the first line matching `Month D, YYYY H:MMAM` (the Created/Uploaded stamps at the bottom don't match because of their ` UTC` suffix or come later); `Product` → game (`Trading Card Game` → tcg, `Video Game` → vgc); `Format` verbatim; `Event Type` and the series name (`Premier Event Series` shows up twice — as the Event Type's value and as a label, the parser skips the value line); the `Address` block joined with `, ` minus the trailing two-letter country → location; `Website` → external URL when it is `http(s)`; `Junior`/`Senior`/`Masters`/`Total Players` counts; `Status` under `About`.
- Category is a keyword map over event type + series + name: League Cup → `cup`, League Challenge → `challenge`, Prerelease → `prerelease`, demo → `demo`, anything else → `others` (a Premier Event Series lands there). Editable before creating.
- The event's name is never the Play! title: it is composed by `composeEventName` (pure, unit-tested; PL-20) as `<type> <store> Q<n> <GAME>` — "League Cup Dune Cómics Q1 TCG", "Mid Year Celebration War Lotus TCG". The type is the series line (fallback: event type, then title) minus its leading game token (TCG / VGC / GO) and minus "Season n", which becomes `Qn`; the store is our store name when the League ID matched one (or the fixed store on a store console), else the page's Activity Group as printed; the game comes from Product, or the series token when Product is missing. Missing pieces are skipped; the form caps it at 100 chars and it stays editable. This is why the form resolves the store before filling the fields.
- Filled fields: name (composed as above), subtitle (series or event type, unless it equals the name), category, game, date (as a `datetime-local` value, i.e. wall-clock time interpreted in the browser exactly like a typed one), location, external URL, tournament id, initial status (`Complete` → `complete`, otherwise `open`) and capacity = Total Players only when the paste says Complete (a historic record; for an upcoming event the count is meaningless).
- Store and league, in two steps (0045). What the Play! site calls a "League" is the store/organiser and its id never changes (WAR LOTUS STORE = `6236068`, shared by the TCG and VGC seasons and by next year's), so the paste's League ID is matched against `stores.play_league_id` (managed on `/admin/stores`). A hit selects the store; then `matchSeasonLeague` (`lib/season-match.ts`, pure, unit-tested) picks the season among that store's leagues: same game as Product, same format as the page's Format line (`formatFromPlay`: Standard → `standard`, GLC/Gym Leader → `glc`, any VGC → `champions`, unknown → not filtered), and `starts_month..ends_month` covering the event's month (a league with no range can't be ruled out). Live seasons win over archived ones; archived ones are only used when nothing live fits (a historic event from last season). Exactly one hit selects it; zero or several leave the league picker empty with a note saying which — the event then hangs off the store only unless the TO picks a league by hand. No store for the id, or no League ID at all, also warns. Store and league can always be picked by hand, and the league picker only lists the chosen store's seasons.
- The only hard failure is a text with no Tournament ID (`PlayPasteError`) — everything else missing just leaves its field empty.

`create_event(…, p_league_id uuid, p_tournament_id text, p_status text, p_store_id uuid)` validates the league and store exist, the status is one of open/closed/complete, and raises on a tournament id already in use (the partial unique index backs it up for direct updates). What the links buy: the event header shows "Tienda: <name>", "Liga: <name>" linking to the league, and the tournament id; the league page lists its events in an "Eventos de la liga" card (`listLeagueEvents`) and shows its store as a badge. Nothing else changes — a linked event is still a standalone event with its own registration, staff and TOM import; it does not feed league standings.

### Import from the locator (pokedata.ovh, PL-21)

The Play! organiser site still has no API, but the public event locator does through https://pokedata.ovh/events/api (help at `/events/api/help`): one GET returns every announced League Cup / League Challenge in a zone and date window as JSON. `/admin/events/import` (`app/admin/events/import/page.tsx`, `requireAdmin`) queries `_tcg/cups/challenges/_vg/cups/challenges` for 30 km around Granada (`POKEDATA_ZONE` in `lib/pokedata.ts`: 37.1773, -3.5986) from today for 120 days (`pokedataWindow`, app timezone), `cache: "no-store"`. An API failure renders as a message; nothing else on the page depends on it.

Per record the API gives `type` (League Cup / League Challenge), `name` (the TO's title), `when` / `date` / `time` (wall-clock local time, no zone), `shop`, `street_address`, `city`, `pokemon_url` (…/play-pokemon-tournaments/26-09-005734/ — the tournament id lives in it), `league` (the Play! League ID = our store), `product` (`tcg` / `vg`), `cost`. No format, no series line, no status for upcoming events. `mapPokedataEvent` turns that into a `PokedataEvent`: tournament id from the URL, `playLeagueId`, game (`tcg` → tcg, `vg` → vgc, anything else unsupported), category via `categoryFromType`, the wall-clock time converted to an instant in Europe/Madrid by `localToIso` (the paste does the same conversion in the browser; the import runs on the server, so the zone is explicit — two-pass offset measurement so DST switch days land right), cost as a number (blank → 0), and the Play! season quarter from the date (`playSeasonQuarter`: seasons roll on September — Season 1 = Sep–Nov, confirmed for the 2027 series, then Dec–Feb, Mar–May, Jun–Aug; the season is named after the year it ends in). From the quarter it synthesises the series line the Play! page would print ("TCG League Cup Season 1"), so `proposedEventName` can feed `composeEventName` unchanged and the import names events exactly like the paste: "League Cup Dune Cómics Q1 TCG"; the series line becomes the subtitle.

The page resolves every row against our data: the League ID against `stores.play_league_id`, then `matchSeasonLeague` on the store's leagues with the format the page would show (`seasonFormatFor`: Standard for TCG, Champions for VGC) and the event month, and the tournament id against `events.tournament_id`. Each row (`components/pokedata-import.tsx`, `ImportRow`) shows the proposed name, game, date, cost, city, the Play! shop and, when matched, our store and league (or "Ninguna liga encaja" / "Varias ligas encajan"), the tournament id, a link to pokemon.com, and a state: **ready** (checkbox), **already imported** (link to the event), **unknown store** (League ID shown so it can be added on `/admin/stores` — never auto-created), **unsupported product**, **no tournament id**. "Seleccionar todos los importables" + "Importar seleccionados (n)" post the tournament ids to `importPokedataEventsAction`, which trusts nothing else from the browser: it re-fetches the API, resolves store and league again and calls `create_event` per event with status `open`, `p_cost` / `p_location` (street address) / `p_external_url` (pokemon.com page) / `p_tournament_id` / `p_store_id` / `p_league_id` (only on a single season match), category, subtitle, no capacity, default list lock, and `p_list_required` / `p_allow_guest_lists` both on for cups and challenges (`requiresListByDefault`, PL-24). Results come back per event (created + link, or the error), and the page re-renders so imported rows flip to "Ya importado". Everything created is a normal standalone event, editable afterwards like a pasted one. No migration: it all fits the 18-arg `create_event` from 0048.

### Stores (0045)

`stores` (id, name, slug unique, `play_league_id` digits-only with a partial unique index `stores_play_league_id_key`, created_by, created_at). World-readable; insert/update/delete by site admins through RLS (`is_site_admin()`), creation through `create_store(p_name, p_play_league_id)` (slugifies, refuses a duplicate Play! id with a readable raise). `leagues.store_id` and `events.store_id` are nullable FKs with `on delete set null`, so deleting a store detaches its rows without deleting anything. 0044's `leagues.play_league_id` and its index were dropped here (nothing had been set). `lib/stores.ts` has `Store`, `listStores`, cached `getStoreById`; `app/actions/stores.ts` has `createStoreAction` / `updateStoreAction` / `deleteStoreAction`; `/admin/stores` (`app/admin/stores/page.tsx` + `components/store-admin.tsx`) lists every store with an inline name/Play! id editor, the number of leagues and events attached, a confirm-delete, and a create form. Linked from the user menu ("Tiendas"). No public store page yet — the store is a label on league and event headers.

### Store admins (0046, PL-17)

`store_admins(store_id, user_id, role owner|admin)` mirrors `league_members`: world-readable, no direct write grants, moved only through `add_store_admin(p_store, p_user, p_role)` / `remove_store_admin(p_store, p_user)` (owners add/remove admins; only site admins add/remove owners; re-adding updates the role, an owner cannot be demoted by another owner). `is_store_admin(uuid)` / `is_store_owner(uuid)` (site admins always pass). The 0005/0010 helpers `is_league_admin`, `is_league_owner`, `is_event_admin`, `is_event_owner` were redefined to also accept admins of the league's / event's store, so every RLS policy and RPC built on them opens to store admins with no other change; hard deletes stay site-admin only. `create_league` / `create_event` (same signatures) accept an admin of `p_store_id`; without a store they remain site-admin only. The `stores` update policy is `is_store_admin(id)`; insert/delete stay site-admin.

Code: `lib/stores.ts` adds `getStoreBySlug`, `listStoreAdmins`, `listAllStoreAdmins`, `listProfilesForPicker`, `listAddableStoreUsers`, `isStoreAdmin`, `isStoreOwner`, `listMyStores` (the membership checks call the SQL helpers via RPC, as `isLeagueAdmin` / `isEventAdmin` now do). `app/actions/stores.ts`: `addStoreAdminAction` / `removeStoreAdminAction`; `updateStoreAction` is gated by `isStoreAdmin` instead of `requireAdmin`. `/stores/[slug]/admin` (`app/stores/[slug]/admin/page.tsx`, gate `isStoreAdmin` → redirect `/`) is the store console: `StoreDetailsForm`, the store's leagues (view / manage links) with `CreateLeagueForm fixedStoreId`, its events with `CreateEventForm fixedStoreId` (store select hidden; a pasted page whose League ID is another store's raises `pasteStoreMismatch` and keeps the store — `lib/paste-store.ts` `resolvePasteStore`, unit-tested), and `StoreRoster` (owners manage admins; the role select only shows for site admins). `/admin/stores` rows carry the same roster plus a link to the console. The user menu lists the stores the user is on the roster of. Form label bundles live in `lib/form-labels.ts` (`eventFormLabels`, `leagueFormLabels`), shared by `/admin/events`, `/leagues` and the console.

## Prize budget (0052, PL-29)

Cups (and any standalone event) get an admin-only "Presupuesto de premios" card in Gestión, right under the edit form. It works out what the entry fees bring in, what goes out per player to the venue and the judge, what the entry packs cost when everyone gets one, any fixed extra cost (with a free-text concept: material, junior prizes…), and splits what is left across the top cut in whole units only — whole packs at the pack's value, or whole euros of store cash; the euros a whole unit does not cover show as "sobrante", a negative remainder as "déficit". Nothing about it is public except the summary the TO publishes.

- Player count: the players imported from TOM (`countTdfPlayers`, a head count on `event_tdf_players`). While nothing is imported the card falls back to the registered count and says so ("estimación hasta importar el .tdf"). The entry fee is the event's own `cost`, edited in the event form.
- Inputs: venue €/player, judge €/player, entry pack yes/no, pack value, extra costs + concept, prize kind (packs / store cash), top cut (Top 2 / 4 / 8 / 16 or any size up to 64) and one integer percentage per placing. Changing the cut size resets the percentages to the preset (`defaultShares`: fixed tables for 2/4/8/16, a descending harmonic split otherwise); "Reparto por defecto" does the same on demand. Percentages that don't add to 100 are taken as weights (the sum turns red as a hint, nothing blocks).
- Prefill: the event's saved budget (`event_prize_budgets`), else the store's defaults (`store_prize_defaults`, edited on the store console's "Premios por defecto" card — `StorePrizeDefaultsForm`, `saveStorePrizeDefaultsAction`), else zeros; the card says which.
- Maths: `lib/event-prizes.ts` (pure, unit-tested). `computePrizeBudget` returns gross, the four deductions, remaining, `potUnits` (floor of remaining ÷ unit), leftover and one award per placing; `splitWhole` distributes the whole units by largest remainder so the awards always add up to the pot exactly, earlier placings winning ties. `prizeSummaryText` builds the public text ("1º: 12 sobres … Sobre de inscripción para todos los participantes"), skipping placings that get nothing.
- UI: `components/event-prize-budget.tsx` (client, `useTranslations("eventPrizes")`) recomputes on every keystroke and previews the text; the hidden fields carry the switch, the kind, the cut size and the shares as a comma list. Two submit buttons on one form: "Guardar" and "Guardar y publicar en Premios".
- Action: `saveEventPrizeBudgetAction` (`app/actions/event-prizes.ts`) validates (money ≥ 0, comma decimals accepted, integer shares, cut 1–64) and upserts the row; with `intent=publish` it recomputes server-side from the saved values and the same player count rule, and writes the summary into `events.prizes` — the public Premios card — refusing when the pot is 0. The browser's numbers are never trusted for what players read.

Assumption baked in: one pot per event. Junior/Senior side prizes go through "otros costes" rather than a per-division split.
