# Project League — repository audit (2026-08-21)

Snapshot of what is in the repo today, how healthy it is, and what stands out. Ticket: `jira-tickets/PL-4-InReview.md`. Everything below was read from the working tree at commit `3239c04` (main, clean working tree) and from the checks listed in the "Health checks" section; nothing was changed in the code as part of this audit.

## 1. What the project is

League and tournament tracker for the Pokémon Granada community (TCG and VGC). Two kinds of activity: leagues (recurring, site-run: league → session → round → match, Swiss pairing, standings, prize pool per trimestre/year) and standalone events (one-off tournaments: registration/waitlist, private decklists, archetype tracking, pairings imported from TOM `.tdf` files, player self-reports as a signal for the judge). Spanish UI, Google-only login, players decoupled from accounts (managed players, claim/approve, merge). Live at `league-tracker-granada.vercel.app` with two game-specific aliases (`pkmgranadatcg` / `pkmgranadavgc` `.vercel.app`) that land on the home page pre-filtered.

## 5. Findings

Ordered by how much they matter. Each one says what was actually verified.

### 5.1 Creating or editing a session from the UI fails against the live DB (confirmed)

`createSessionAction` / `updateSessionAction` in `app/actions/sessions.ts` call `create_session` with 6 named args (`p_league, p_name, p_starts_at, p_location, p_cost, p_capacity`) and `update_session` with 5. Migration `0033_session_format.sql` dropped those signatures and recreated both functions with three extra required params (`p_best_of`, `p_rounds_planned`, `p_round_timer_minutes`); no later migration restored an overload and the forms (`create-session-form.tsx`, `edit-session-form.tsx`) never send those fields. Verified against the live project with the anon key: the 6-arg call returns `PGRST202 "Could not find the function public.create_session(p_capacity, p_cost, p_league, p_location, p_name, p_starts_at)"` while the 9-arg call reaches the function body (`Not allowed`, as expected without a session). This has been the state since commit `05af81e` (2026-07-19). Sessions in use were presumably created through `generate_league_sessions`, which is why it went unnoticed; the per-session "Editar sesión" form is affected the same way. `docs/features/sessions-rounds.md` already carries a "worth double-checking" note on exactly this. Fix is small: pass the three params (the `best_of`/`rounds_planned`/`round_timer_minutes` columns already exist and the session page already reads them) or add `default` values in a new migration. Needs its own ticket.

### 5.2 Browser QA on shipped tickets is still open

PL-2 is In Review with 11 browser scenarios unchecked (round lifecycle, drop → re-pair, leave-as-drop, regressions). PL-1 and PL-3 are marked Done but each still lists unchecked browser/SQL items (6 and 7). Everything that was verified was verified via tests, tsc, build, REST probes and the prod display page — nobody has clicked through the flows. Given 5.1 slipped through for a month for the same reason, the click-through is worth doing.

### 5.3 Test coverage stops at pure logic

Pairing, scoring, standings, profile aggregation, prize pool, deadlines and the TDF parser are well covered. Nothing exercises server actions, RPC signatures, RLS, or rendering — the class of bug in 5.1 cannot be caught by the current suite. Cheapest next step: a script (or a vitest file gated on env) that lists every `supabase.rpc("name", {...})` call in `app/actions/` and checks the arg-name set against the live PostgREST schema, plus the RLS assertions from `PLAN.md`'s verification list (non-admin cannot create a league, cannot read another player's list, cannot report a match they're not in).

### 5.4 Everything except lists is world-readable

Public `select using (true)` policies exist on `players` (including `pokemon_id`, `game_id`, first/last name), `profiles`, `session_participants`, `event_registrations`, `matches`, `rounds`, `event_matches`, `event_standings`, `league_members`, `event_admins`, `event_staff`, `leagues`, `sessions`, `events`, `archetype_customs`. Only `event_lists`, `event_tdf_players`, `event_tdf_imports`, `player_decks`, `admin_allowlist` and private archetype picks are restricted. The UI hides Pokémon IDs and the event roster from non-admins, but the REST API does not — anyone with the anon key (which is public by design) can list every player's Pokémon ID and real name. Decide whether that's acceptable for this community; if not, the `players` policy is the one to tighten (expose a view or restrict columns), and `docs/features/events.md` already notes the roster gap.

### 5.5 Lint errors and a six-minute typecheck

The two `set-state-in-effect` errors (`round-timer.tsx`, `theme-toggle.tsx`) are real rule violations; `rounds-tabs.tsx` was already fixed the right way in PL-2 (adjust state during render / `useSyncExternalStore`), so there is a pattern to copy. `npm run lint` currently exits non-zero, which would block any future CI. The typecheck inside `next build` taking ~6 minutes (vs ~30s compile) is worth a look — `tsconfig.json` includes `.next/types/**` and `.next/dev/types/**`, and `tsconfig.tsbuildinfo` is 174 KB; a stale `.next` may be inflating it.

### 5.6 Docs drift

- `README.md` is still create-next-app boilerplate; `DEPLOYMENT.md` and `docs/features/` are the real docs. A 15-line README pointing to them (stack, `npm test`/`build`, deploy rule, ticket convention) would help anyone landing in the repo.
- The prize pool is undocumented: `lib/prize-pool.ts`, `lib/prize-awards.ts`, `league_prize_awards` (0038), `awardLeaguePrizeAction`/`revokeLeaguePrizeAction` and the league home/admin UI are not in `docs/features/leagues.md` (the word "prizes" there refers to the free-text field).
- `docs/features/leagues.md` says `locations`/`default_location` are "not confirmed in the migration set"; they are in `0007_session_refinements.sql` and `0025_league_weekly_schedule.sql`.
- `docs/features/archetypes.md` lists `participant-archetype-editor.tsx`, which does not exist (the editor lives inside `participants-list.tsx`).
- `PLAN.md` is the July plan and diverges from what shipped: no `lib/merge.ts`/`lib/waitlist.ts` (both live in SQL), no `/agenda` or `/events` routes (landing page does it), sessions moved under `/leagues/[slug]/sessions/[sessionSlug]`, events gained TOM import and on-site reporting, `win_value` default is 3 not 1, archetypes come from the Pokédex + customs rather than icon uploads. Worth either marking it historical at the top or deleting it.

### 5.7 Smaller observations

- `/settings` is a placeholder page reachable from the user menu.
- `proxy.ts` hardcodes the two game hostnames; fine for now, but moving to an env var avoids a deploy when domains change.
- No CI: tests, lint, tsc and build run only when someone runs them locally before pushing (the DEPLOYMENT.md procedure). A GitHub Actions workflow running `npm ci && npm test && npx tsc --noEmit && npm run lint && npm run build` on push would have caught nothing about 5.1 but would hold the line on 5.5.
- No `prettier`/formatter config; formatting is consistent anyway because everything went through one pipeline.
- Dependencies are within a minor of latest; `next` 16.3.2 is the one to read release notes for before bumping.

## 6. What is solid

The domain logic (pairing with no-rematch lookahead, repair, scoring/OWP, league standings, TDF idempotent import keyed on `(division, number)` and `pair_key`) is pure, tested and documented with the reasoning behind each rule. All writes are RPCs with server-side authorization checks (`is_site_admin` / `is_league_admin` / `is_event_admin`), so the client never decides permissions. Realtime refresh is used where it matters (session page, displays, events) with a poll fallback. Docs in `docs/features/` are genuinely kept current with the code, and the deploy procedure is written down including the traps that already bit once.
